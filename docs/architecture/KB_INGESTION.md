# DOCENTE OS — Knowledge Base & Asset Ingestion

Status: CANONICAL_V1

## Decision

Every asset captured, uploaded, received or generated by DOCENTE OS enters a canonical Knowledge Base pipeline. The original source is never replaced by an AI-derived representation.

Canonical flow:

`ORIGINAL SOURCE -> KNOWLEDGE ASSET -> NORMALIZED DOCUMENT -> KNOWLEDGE UNITS -> RELATIONS -> OPERATIONAL USE`

Operational use includes Planner tasks, communications, documents, calendar events, training items, classes/UDA, lesson logs and archive records.

## Why

DOCENTE OS must not become a collection of disconnected files. A circular, email, PDF, DOCX, image, calendar item, note or generated document must become searchable, traceable knowledge while preserving evidentiary provenance.

## Storage responsibilities

- External provider (Drive/Gmail/Calendar/upload source): authoritative original payload/file where applicable.
- PostgreSQL/Supabase: canonical metadata, normalized knowledge, relations, workflow state and audit.
- Knowledge Base: derived text/structure suitable for search and orchestration; never a silent replacement of the source.

## Canonical entities

### KnowledgeAsset
Represents the immutable captured source identity.

Key fields:
- workspace / academic year
- asset kind and source provider
- original name and MIME type
- external/source locator
- SHA-256 when bytes are available
- size
- captured timestamp
- processing status
- source metadata
- creator

Duplicate policy: an identical byte hash in the same workspace is recognized as the same source content, but provider/source metadata may still be preserved separately in later versions if needed.

### KnowledgeDocument
Normalized, human-readable representation of an asset.

May contain:
- normalized plain text
- normalized Markdown
- title
- document type
- language
- concise summary
- structured extraction JSON
- processing version
- full-text search vector

Examples of document types: `CIRCULAR`, `TEMPLATE`, `ATTESTATION`, `TEACHING`, `COMMUNICATION`, `GENERAL`.

### KnowledgeUnit
Small traceable semantic unit extracted from the normalized document.

Initial unit types:
- `CHUNK`
- `ENTITY`
- `DATE`
- `DEADLINE`
- `ACTION`
- `PERSON`
- `CLASS`
- `TOPIC`
- `RULE`

Every automatically extracted unit carries confidence and validation status. AI output is therefore evidence-linked and reviewable rather than promoted silently to fact.

### KnowledgeLink
Generic typed relation from a KB asset/unit to another application object.

Examples:
- `ACTION -> PLANNER_TASK`
- `DEADLINE -> PLANNER_TASK`
- `ASSET -> COMMUNICATION`
- `ASSET -> DOCUMENT`
- `TOPIC -> UDA`
- `ATTESTATION -> TRAINING_ITEM`
- `DATE -> CALENDAR_EVENT`

The target is represented as application type + stable target reference. This keeps the KB provider-neutral.

### KnowledgeIngestionRun
Tracks each transformation stage, version, status and failure without overwriting previous evidence.

Stages may include:
- `CAPTURE`
- `TEXT_EXTRACT`
- `NORMALIZE`
- `CLASSIFY`
- `STRUCTURE`
- `CHUNK`
- `ENRICH`
- `INDEX`
- `LINK`

## Transformation policy by asset type

- PDF: preserve original; extract selectable text; OCR only when no usable text exists; normalize page/section boundaries; retain page provenance.
- DOCX/ODT: preserve original; extract headings, paragraphs, tables and metadata; normalize to Markdown + structured blocks.
- XLSX/CSV: preserve original; produce schema-aware structured JSON/table summaries rather than flattening blindly to prose.
- Images/scans: preserve original; extract only useful textual/document semantics; retain image as evidence.
- Gmail: retain provider IDs and minimal message metadata; normalize body/attachments into KB without duplicating the entire mailbox unnecessarily.
- Calendar: normalize event facts and links; do not treat Calendar as task storage.
- User notes: native text asset, immediately normalized.
- Generated documents: store generation provenance and links to source units used.

## Human validation

The KB distinguishes extraction from validation:
- `AUTO`: machine-derived and not yet confirmed;
- `REVIEWED`: human-validated;
- `REJECTED`: explicitly rejected.

Institutional decisions, deadlines inferred from ambiguous language and document-generation actions remain subject to human validation.

## Search strategy V1

V1 uses PostgreSQL full-text search with Italian configuration plus structured JSON filters and explicit relations. Vector embeddings are a secondary index planned later; they are not the canonical representation.

This avoids provider lock-in and allows deterministic search for names, dates, classes, document types and exact institutional terminology.

## Privacy and isolation

All KB tables are workspace-scoped and protected by RLS. No anonymous access. Derived content inherits the visibility boundary of the source asset.

## Application ports

Planned provider-neutral boundaries:

- `KnowledgeAssetRepository`
- `KnowledgeDocumentRepository`
- `KnowledgeSearchPort`
- `AssetTransformerPort`
- `KnowledgeEnrichmentPort`
- `KnowledgeLinkRepository`

Provider adapters may implement PDF/DOCX parsing, Google data acquisition or AI enrichment, but domain objects do not import provider SDK types.

## First implementation slice

Migration `0006_knowledge_base.sql` introduces:
- `knowledge_assets`
- `knowledge_documents`
- `knowledge_units`
- `knowledge_links`
- `knowledge_ingestion_runs`

with workspace RLS and full-text indexes.

## Acceptance gates

1. Original source identity remains immutable.
2. Derived representation is separately versioned.
3. Every unit can be traced back to a document/asset.
4. Cross-workspace access is denied.
5. Automated extraction cannot masquerade as human-validated knowledge.
6. Search works without requiring embeddings.
7. Planner and future modules link to KB rather than copy source content.
8. A failed transform leaves the original asset available and records the failure.
