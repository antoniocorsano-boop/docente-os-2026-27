# DOCENTE OS — Knowledge Base & Asset Ingestion

Status: CANONICAL_V1

## Decision

Every asset captured, uploaded, received or generated by DOCENTE OS enters a canonical Knowledge Base pipeline. The original source is never replaced by an AI-derived representation.

Canonical flow:

`ORIGINAL SOURCE -> KNOWLEDGE ASSET -> PROCESSING GENERATION -> NORMALIZED DOCUMENT -> KNOWLEDGE UNITS -> RELATIONS -> OPERATIONAL USE`

Operational use includes Planner tasks, communications, documents, calendar events, training items, classes/UDA, lesson logs and archive records.

## Why

DOCENTE OS must not become a collection of disconnected files. A circular, email, PDF, DOCX, image, calendar item, note or generated document must become searchable, traceable knowledge while preserving evidentiary provenance.

## Storage responsibilities

- External provider (Drive/Gmail/Calendar): authoritative original payload/file where applicable.
- Direct uploads: authoritative binary is stored in the private Supabase Storage bucket `knowledge-assets`, scoped by workspace path and RLS.
- PostgreSQL/Supabase: canonical metadata, normalized knowledge, relations, workflow state and audit.
- Knowledge Base: derived text/structure suitable for search and orchestration; never a silent replacement of the source.

## Canonical entities

### KnowledgeAsset
Represents the immutable captured source identity.

Key fields:
- workspace / academic year
- asset kind and source provider
- original name and MIME type
- external/source locator
- SHA-256 when bytes are available
- size
- captured timestamp
- processing status
- source metadata
- creator
- `current_generation_id`: pointer to the only derivative generation used by current search/UI.

### KnowledgeProcessingGeneration
Represents one complete attempt to transform the same immutable asset.

States:
- `RUNNING`
- `SUCCEEDED`
- `FAILED`

Each asset has monotonically increasing `generation_no`. A generation becomes current only after normalization, enrichment and indexing all succeed. Failed generations remain in the audit trail and never replace the last successful current generation.

### KnowledgeDocument
Normalized, human-readable representation of one asset generation.

May contain normalized text/Markdown, title, document type, language, summary, structured extraction JSON, processing version and full-text index.

### KnowledgeUnit
Small traceable semantic unit extracted from the normalized document.

Initial unit types: `CHUNK`, `ENTITY`, `DATE`, `DEADLINE`, `ACTION`, `PERSON`, `CLASS`, `TOPIC`, `RULE`.

Every automatically extracted unit carries confidence and validation status. For PDFs, units retain `source_page` so the derivative can be traced back to the original page.

### KnowledgeLink
Generic typed relation from a KB asset/unit to another application object. Existing links stay tied to the exact historical unit that created them even after reprocessing.

### KnowledgeIngestionRun
Tracks each transformation stage, version, status and failure. Stages include `CAPTURE`, `TEXT_EXTRACT`, `NORMALIZE`, `CLASSIFY`, `STRUCTURE`, `CHUNK`, `ENRICH`, `INDEX`, `LINK`.

## Transformation policy by asset type

- PDF: preserve original; extract selectable text page-by-page using `unpdf`; retain page provenance. Visual OCR is invoked only for pages without usable native text, and never replaces usable native extraction.
- DOCX: preserve original; extract raw textual semantics using `mammoth`; never render unsanitized source HTML.
- TXT/Markdown: preserve uploaded original; extract UTF-8 text and index immediately.
- XLSX/CSV: preserve original; produce schema-aware structured JSON/table summaries rather than flattening blindly to prose.
- Images/scans: preserve original; extract only useful textual/document semantics through the provider-neutral visual extraction port; retain image as evidence and mark derivatives for human review.
- Gmail: retain provider IDs and minimal message metadata; normalize body/attachments without duplicating the whole mailbox.
- Calendar: normalize event facts and links; do not treat Calendar as task storage.
- User notes: native text asset, immediately normalized.
- Generated documents: store generation provenance and links to source units used.

## Implemented file intake V1

Private bucket `knowledge-assets` accepts PDF, DOCX, TXT, Markdown, PNG, JPEG and WebP with a 20 MB per-file limit.

Upload flow:

`UPLOAD -> PRIVATE STORAGE -> KNOWLEDGE ASSET -> GENERATION -> BYTE LOAD -> TRANSFORMER -> ENRICHMENT -> UNITS -> INDEX -> PUBLISH CURRENT`

If the first transformation fails, the asset is `FAILED` but the original remains available. If a later reprocessing fails, the previous successful generation remains current and searchable.

## Generation-safe Rielabora

`Rielabora` is now implemented with these invariants:
1. read the same immutable original;
2. create `generation_no = previous max + 1`;
3. create a generation-specific normalized document and units;
4. complete all transformation/indexing stages;
5. mark the generation `SUCCEEDED`;
6. only then update `KnowledgeAsset.current_generation_id`;
7. if any stage fails, mark only the new generation `FAILED` and preserve the previously current generation;
8. never delete historical derivative generations or their validated links.

Search, recent-asset summaries and asset detail operate on the current generation only.

## Human validation

The KB distinguishes extraction from validation:
- `AUTO`: machine-derived and not yet confirmed;
- `REVIEWED`: human-validated;
- `REJECTED`: explicitly rejected.

Institutional decisions, ambiguous deadlines and document-generation actions remain subject to human validation.

## Search strategy V1

V1 uses PostgreSQL full-text search with Italian configuration plus structured JSON filters and explicit relations. Vector embeddings remain a secondary future index, not the source of truth.

## Privacy and isolation

All KB tables are workspace-scoped and protected by RLS. No anonymous access. Derived content inherits the source asset visibility boundary. Direct-upload binaries use a private Storage bucket whose policies verify workspace membership from the first path segment.

## Application ports

Provider-neutral boundaries include `KnowledgeAssetRepository`, `KnowledgeGenerationRepository`, `KnowledgeDocumentRepository`, `KnowledgeSearchPort`, `AssetContentPort`, `AssetTransformerPort`, `KnowledgeEnrichmentPort`, `KnowledgeLinkRepository`, `KnowledgeIngestionLog`.

## Current implementation slices

- `0006_knowledge_base.sql`: core KB tables, RLS and full-text indexes.
- `0007_knowledge_base_hardening.sql`: immutable provenance and no application DELETE on KB evidence.
- `0008_knowledge_native_original_text.sql`: original text for native NOTE/GENERATED assets.
- `0009_knowledge_asset_storage.sql`: private workspace-scoped file storage.
- `0010_knowledge_processing_generations.sql`: generation-safe derivative publishing and current-generation pointer.
- `0011_knowledge_visual_assets.sql`: private bucket allowlist for PNG, JPEG and WebP sources.
- PDF transformer: `unpdf`, page-aware extraction.
- DOCX transformer: `mammoth.extractRawText`.
- deterministic school communication enrichment: ACTION/DEADLINE candidates requiring human validation.
- `Rielabora`: generation-safe reprocessing with rollback-by-pointer semantics.
- visual extraction adapter: OpenAI Responses file/image input behind `VisualExtractionPort`; configured only server-side.
- mixed PDF extraction: native text retained page-by-page, visual OCR limited to pages without useful text.

## Acceptance gates

1. Original source identity remains immutable.
2. Every derivative belongs to an explicit processing generation.
3. Only a `SUCCEEDED` generation may become current.
4. Failed reprocessing cannot replace a valid current generation.
5. Every unit is traceable to document/asset/generation; PDF units retain page provenance.
6. Cross-workspace database and binary access is denied.
7. Automated extraction cannot masquerade as human-validated knowledge.
8. Search works without requiring embeddings and uses only the current generation.
9. Planner and future modules link to exact KB units rather than copying source identity.
10. Historical generations and validated links are retained for audit.
